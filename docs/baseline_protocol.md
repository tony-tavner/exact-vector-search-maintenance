# Панель точного сравнения статьи A — спецификация E02

18.11.2026; версия 1.2-C1-controls, E02_2026-11-18_01. Это требования к будущим реализациям. Историческая E03 для C0 сохранена; новая E03 для C1 и E04 не выполнялись, результатов скорости нет. B0–B6 обязательны для общего критерия преимущества. Панель выбрана по первичным текстам; реализация, численная сертификация и тесты соответствия предстоят в E03/E04.

## Общая задача и обозначения

`M` — число активных запросов, `N` — число фрагментов, `D` — число документов, `d=768` — размерность. `a` — число изменившихся фрагментов, `a*` — число фрагментов всех затронутых документов, которые приходится просмотреть для восстановления максимума. `A` — число действительно затронутых запросов, `r` — резерв документов, `P` — число пар, не отсечённых применимостью. Стоимость embeddings, фильтров, сортировки, индекса, материализации и таймеры описываются отдельно; выражения ниже характеризуют вычислительные компоненты, а не доказанные оценки конкретной опубликованной работы.

Все методы возвращают один и тот же полный объект из паспорта v2 на одном снимке. Индексируются запросы с фиксированным временем и фильтром. Равенство score обрабатывается по ID. Удаление фрагмента-победителя требует восстановления максимума документа; удаление/потеря применимости документа может потребовать нового документа извне сохранённого top-k. Вставка, смена фильтра с false на true и версия текста также обязательны. Не допускается пропуск партии без проверки.

В строке B1 `a*` (a_star) — расширенный набор фрагментов затронутых документов, а не произведение; точная стоимость выбирается по реализации. Сохранённые scores могут уменьшать повторные dot-операции. Простые совместные варианты (резерв + пакетная проверка + фильтры; выбор полного поиска при большой партии) также подбираются на разработке и сравниваются на валидации. Нельзя сравнить новый индекс только с заведомо неоптимальными раздельными приёмами. Правило переключения фиксируется до финала; оно не выбирает минимальное время задним числом для каждого финального случая.

B3: матрица binary64 на разработке `679×1264×8=6 866 048` байт, **6.54797 MiB**; отдельные документные оценки `679×679×8=3 688 328` байт, **3.51746 MiB**. Для всех записей корпуса лишь арифметическая оценка `1016×1895×8=15 402 560` байт, **14.68903 MiB**. Это размер полезной матрицы, не измеренный RSS: векторы, ID, копии, embedding-процесс и allocator учитываются дополнительно. Финальные scores не вычислялись.

## Что не даёт равного точного конкурента автоматически

- Aker, §4.6, pp.7–8: del-consistency обеспечивает живые результаты, допускает несовпадение с текущим ANNS, вставки отражает лениво.
- SSC, Eq.1–7, p.3: свежий retrieval объединяется с памятью, ACL/freshness-фильтры и utility-ranking. Отсутствует гарантия нашего document-level snapshot top-k. Не сводить SSC к проверке только старых источников.
- RAGCache, §§4–5.1, pp.4–5: кэширование KV tensors генерации после retrieval; не maintenance-алгоритм нашего точного выхода.
- SAH: полный алгоритм использует приблизительный LSH; его известные cone bounds сами по себе не дают точной динамической реализации. Если собственный метод использует эти bounds, до финала нужен точный сравнительный вариант с полной проверкой и учётом обслуживания.
- Influence sets (Stanoi et al., 2001): exact bichromatic 1-NN, в основном 2D NN/range queries; исторический аналог, а не ближайший готовый 768D top-k конкурент.
- TTL/source-only validation — диагностические отрицательные контроли. scikit-learn kneighbors — компонент по строкам, не группирующий документный оператор.

Приближённая панель допускается только отдельно: полное совпадение выдачи, изменение ID/версий, качество–время и предел допустимых ошибок явно заданы. Нулевая ошибка на небольшом тесте не превращает приблизительную гарантию в точную.

## Условия честного запуска в будущих этапах

1. Одни и те же входные снимки, события, последовательность, embeddings/config и правила применимости. Первоначальные результаты и индексы строятся за счёт каждого метода; новый запрос нельзя обслуживать бесплатно заранее готовым ответом.
2. Общие блоки хранения, фильтры, векторизация, канонический числовой путь, число потоков, CPU/GPU и кэш embeddings доступны всем. Настройка резерва/индекса/переключения получает сопоставимый бюджет; лучший вариант определяется на development/validation.
3. Канонический score E01 сохраняется. Векторизация нуждается в проверяемой гарантии численной совместимости, а не только в совпадении нескольких ответов. Все пограничные пересчёты включаются в total; исключать их из времени предлагаемого метода нельзя.
4. Отчёт содержит cold lifecycle от исходных текстов и отдельно готовые-векторы. В cold-режиме каждый измеряемый запуск физически выполняет необходимые embedding-вызовы и проверяет конфигурацию/идентичность сравниваемых векторов. Если повторяемость инференции не подтверждается, этот режим дорабатывается; арифметическая сумма чужого времени embeddings и ядра не выдаётся за прямой сквозной замер.
5. Начало/конец таймера, правила загрузки файлов, кеширования, публикации, проверки готовности, измерение peak RSS дерева процессов, порядок запусков и timeout фиксируются до финала. Общая плата за embeddings не вычитается из основной метрики ради более красивого ускорения.
6. Пороговые/табличные индексы не получают информацию будущих событий. Изменение применимости без изменения вектора обязано активировать нужные проверки. Порядок нескольких событий одного ID и атомарное конечное состояние едины для всех.
7. Неудавшийся запуск сохраняется с причиной; сравнение нельзя ограничить только случаями, где наш метод завершился. При OOM конкурента показать лимит и рост памяти, не присваивать бесконечное ускорение.
8. Собственные упрощённые варианты: без индекса влияния; без резерва; без групповых сводок. Если удаление проверки нарушает точность, это отрицательный контроль, а не допустимая точная абляция. Их код/замеры выполняются позже, не в E02.

## Проверяемый перенос B4/B5 и границы приёмки

Исходные тексты: `literature/sources/E02_2026-11-17_02/simpfer_fulltext/source.pdf` и `rmips_complete/source.pdf`. Авторские ZIP и извлечённый код сохранены в `simpfer_code/` и `simpferpp_code/`; лицензия MIT. Полные локаторы, версии и замечания статического просмотра — в `literature/primary_review_E02.md` и `source_manifest.json`. Оригиналы не исправляются; будущая адаптация получает отдельную версию и журнал отличий.

| Компонент | Обязательное правило переноса |
|---|---|
| Роли | users U → зарегистрированные запросы; item candidate → изменённый документ с его фрагментами; не менять роли местами |
| Score | max canonical fragment scores. Нижний k-й порог обосновывается k различными применимыми документами; повторные фрагменты одного документа не увеличивают k |
| Верхняя граница | Для документа учитывать все его фрагменты; norm-bound использует максимум их норм. Граница должна быть консервативна в машинной арифметике; сомнение означает проверку, не отсечение |
| Фильтры | Границы строятся по применимому для каждого запроса корпусу; общие разбиения доступны всем. Не применить порог из более широкого корпуса к узкому фильтру |
| Удаление/ухудшение | Сначала проверить старые зависимости и пригодность свидетелей порога; при потере применимого свидетеля обновить/ослабить границу или выполнить точный fallback. Старый завышенный порог использовать запрещено |
| Вставка/улучшение | Проверить новый max и применимость, в том числе кандидата вне прежней выдачи. При изменении состава партии сертификат относится к правильному снимку; если это не обосновано, использовать полный пересчёт |
| Текст/metadata | Изменение версии без изменения score всё равно обновляет выход; изменённая применимость может активировать поиск без нового embedding |
| Полный результат | Восстановить упорядоченный top-k документов и представителей, не только множество затронутых запросов или r_count. Публиковать после завершения атомарной партии |
| Числа/равенства | Отказ от map<score,id>, теряющего ties; поддержка отрицательных оценок, пустых/малых корпусов и UTF-8 границ; float32 Eigen не считается равным fsum |
| Код/потоки | Проверить последний элемент/остаточный блок и счётчики OpenMP; дать одинаковое число потоков и scorer всем конкурентам; авторский код не запускать без общей приёмки |

Реализация не обязана быть построчным портом демонстрационного C++; достаточны faithful algorithm, таблица соответствия и отдельные изменения для контракта A. E02 устанавливает техническую реализуемость по определениям/псевдокоду/коду; доказательство безопасности адаптации выполняется в E03, её реализация и differential/property-проверки — в E04. Сейчас ни один скачанный baseline не помечен как прошедший контракт A.

До финала каждую обязательную семью представляет один выбранный на validation и зафиксированный вариант. B2 фиксирует также политику управления kmax; B5 — способ точного поддержания порогов; B6 — политику переключения. Все варианты разведки и проигрыши сохраняются. Основных контрастов m=7; если по новой литературе/вкладу добавится обязательный вариант, новая версия критериев и поправка множественности фиксируются до финала. Исключение неудобного B4/B5 или его непроверенная адаптация возвращает E02/E04 и запрещает общий вывод о преимуществе.

## Усиления для проверки C1 — R02_2026-11-18_01

Семейства B0–B6 не исключаются и не ослабляются. Разработчик обязан дать B3/B5/B6 одинаковые доступные cache/filter/batch/численные примитивы, а не сравнивать C1 с C0 на Python. Новые controls относятся к проверке конкретного механизма C1 и выбору сильного варианта B6 до финала:

| Контроль | Что разрешить/проверить | Что опровергает |
|---|---|---|
| C1-control-MARGIN | Per-query max/runner-up, witness ID, version invalidation, безопасные norm-delta/gap проверки; old scores использовать из B3 либо оплачиваемого cache | Выигрыш от одной лишь обычной проверки запаса, а не C1 |
| C1-control-SEPARATE-BOUNDS | Те же query blocks и безопасные геометрические примитивы; отдельные upper нового фрагмента и lower сохранившегося свидетеля, плюс absolute score/reserve threshold | Нужность парной коррелированной границы; первый 2D пример недостаточен, поскольку отдельные интервалы там тоже могут сработать |
| C1-control-FLAT-CERTIFICATE | Тот же двусторонний block predicate и тот же backend, но простой обход существующих reserve postings без специальной факторизации | Самостоятельную пользу факторизованного отношения влияния; отсутствие выигрыша требует сузить/пересмотреть вклад |
| C1-control-UNCACHED | C1 без межпартийных certificate caches (в A-E02-C1-0.1 сертификаты и так одноразовые) | Не приписывать выигрыш несуществующему persistent certificate механизму |

MARGIN и SEPARATE-BOUNDS доступны как варианты B6/B3/B5 по совместимости. FLAT-CERTIFICATE — обязательный диагностический контроль/абляция самого кандидата, не независимая внешняя статья. Если простая композиция воспроизводит весь C1 при той же стоимости/памяти, она не исключается из отчёта: самостоятельность и заявленный эффект считаются неподтверждёнными.

Один вариант каждой из семи основных семей выбирается на validation и фиксируется до финала. Нельзя выбирать минимальное финальное время по строкам. Наличие дополнительных controls не добавляет незаявленные confirmatory p-values: для отдельного подтверждающего вывода по ним заранее нужна версия статистического протокола и пересчёт множества контрастов. Прежний первичный порог 10%, ресурсы и семь контрастов не изменены.

Сравнивать полную цену build + byte/version validation + embeddings + certified bound + неуспешные попытки + точный engine + postings + publication/read. Общий вывод нельзя строить лишь по числу сэкономленных dot. Неблагоприятные metadata/document insert/delete/config события сохраняются; выбирать их долю ради победы C1 запрещено.
