# C1-O1: доказанный дешёвый сертификат канонического math.fsum

18.11.2026 · E03_2026-11-18_03 / R02_2026-11-18_02 · **A-E03-C1-0.3-bounded-fsum**.
Возврат RW_A_E03_2026-11-18_02. Канонический оператор E01 сохранён:
`s(q,x)=math.fsum(float64(q_i)*float64(x_i))`, фиксированный порядок координат.

**Результат:** ниже доказана конечная равномерная оценка для конкретной локальной реализации и указанной арифметической среды. Она даёт O(p) точных арифметических действий для проверки пары z,w на целом box, без обхода q. Прежняя гипотеза `4u Σ|t|+4η` не объявляется доказанной: она заменена более консервативной оценкой из числа операций. Историческая редакция сохранена в `docs/method_history/A-E03-C1-0.2-audit/`.

## 1. Область теоремы и guards

u=2^−53, η=2^−1074, h=η/2 — **точные рациональные числа**, в том числе h, не представимое положительным binary64. Входные координаты конечные binary64, |q_i|,|z_i|,|w_i|≤2; 1≤p≤2^20. Box имеет конечные фактические границы −2≤l_i≤h_i≤2 и покрывает все q стабильной epoch. Здесь h_i — верхняя координата box, h без индекса — η/2.

Числовая среда: отдельные binary64 RN ties-to-even add/sub/mul, gradual underflow; без FMA, extended precision, FTZ/DAZ и изменения режима во время операции. Для проверенного arm64 это FPCR=0. `math.fsum` и float multiplication связаны с сохранёнными SHA256 бинарных модулей/загруженных инструкций; адреса и ветви разобраны в `fsum_runtime_audit_C1.md`. Теорема не распространяется автоматически на другую сборку Python/CPU.

Проверка хешей/адреса выполняется при создании numeric context; проверка FPCR — в том же worker thread до и после защищённой числовой области. Внутри области запрещены изменяющие FPCR callbacks, signal handlers, сторонние BLAS/FFI, подмена math.fsum/float slots, произвольные __float__/итераторы. Используются обычные неизменные binary64/Python float значения. Две проверки FPCR сами по себе не доказывают отсутствие временной смены режима: это дополнительный явный инвариант среды исполнения. При невозможности обеспечить его BOX не включается. Точное сохранение порядка/продуктов при материализации built-in tuple допустимо и не меняет scorer.

Не прошедший guard ⇒ UNKNOWN, затем обычный точный engine; это не новый допуск ранжирования и не отказ от E01 для остальных входов. Ошибка/нефинитный результат точного engine ⇒ партия не публикуется. MemoryError числовой проверки также не даёт положительного сертификата. Для невалидного/сменившегося числового config нужен прежний режим полной переинициализации.

## 2. Локальная лемма об одном округлении

Для конечного exact результата без overflow стандартная RN binary64 модель с gradual underflow даёт

`|RN(v)−v| ≤ u|v|+h`.

Для нормального диапазона это следует из половины расстояния между соседними значениями, не превышающей u|v|; в subnormal-диапазоне шаг η, поэтому абсолютная ошибка ≤η/2. В точках перехода действует та же объединённая оценка. Для сложения/вычитания v=a±b, для произведения v=ab. Signed zero имеет точное вещественное значение 0; η-члены сохраняются. Overflow исключён конструктивно в §6, а не допущен внутри этой леммы.

## 3. Одна тройка операций: не требуется теорема FastTwoSum

Рассмотрим фактические три операции алгоритма:

`hi=RN(x+y); yr=RN(hi−x); lo=RN(y−yr)`.

Пусть T=|x|+|y|. Перестановка x,y перед тройкой не меняет T. Введём точные ошибки e1,e2,e3. Тогда

`hi=x+y+e1`, `yr=y+e1+e2`, `lo=−e1−e2+e3`.

Из §2 последовательно:

* |e1|≤uT+h;
* |e2|≤(u+u²)T+(1+u)h;
* |e3|≤(2u²+u³)T+(1+2u+u²)h.

Поэтому (для фиксированного u=2^−53):

**P1.** `|(hi+lo)−(x+y)| ≤ (u+3u²+u³)T+(2+3u+u²)h ≤ 2uT+2η`.

**P2.** `|lo| ≤ (2u+3u²+u³)T+(3+3u+u²)h ≤ 3uT+3η`.

**P3.** `|hi|+|lo| ≤ (1+3u+3u²+u³)T+(4+3u+u²)h ≤ (1+4u)T+3η`.

Все коэффициентные ослабления проверены точными рациональными неравенствами в числовом отчёте. Эти выводы не предполагают exact error-free transform, non-overlapping partials, faithful rounding или корректно округлённый fsum. Поэтому отсутствующее исходное доказательство FastTwoSum/финальной поправки не переносится как скрытая предпосылка.

## 4. Накопление partials и значение пропущенного хвоста

Пусть t_1,…,t_p — уже округлённые произведения, A=Σ|t_i|, L=p(p−1)/2. Код вставляет очередной t в массив partials: проходит прежние элементы, сохраняет каждый ненулевой lo, несёт hi дальше и в конце добавляет ненулевой hi. После j входов partials не более j; всего троек ≤L. Запись идёт вперёд в уже обработанную часть массива; ни один старый элемент не пропускается.

Рассматриваем массу S = сумма модулей всех текущих partials/несомого x плюс модули ещё не введённых входов. Ввод очередного t лишь перемещает его из будущих входов; удаления нулей массу не меняют. По P3 после тройки S'≤(1+4u)S+3η. Для j≤L, 4Lu<1:

`(1+4u)^j ≤ 1/(1−4Lu)` и `Σ_{i<j}(1+4u)^i ≤ L/(1−4Lu)`.

Первая оценка следует из бинома: C(j,k)≤j^k и суммы геометрического ряда; вторая — из оценки каждого слагаемого. Следовательно в любой момент

**H = (A+3Lη)/(1−4Lu)**

ограничивает S. По P1 signed drift суммы partials от точной суммы входов не превосходит

**D_acc = L(2uH+2η)**.

Ключевое свойство, не требующее non-overlap: после **последней полной вставки** каждый элемент массива, кроме возможного последнего hi, есть свежий lo этой вставки, поэтому имеет модуль ≤3uH+3η. Если hi=0 и не добавлен, это верно для всех элементов. Начальный hi финального схлопывания берётся с конца. Любой оставшийся неиспользованный хвост, даже при ранней остановке, поэтому ограничен по модулю суммой ≤p(3uH+3η). Пустой массив возвращает 0; при p=1 утверждение также верно.

## 5. Финальное схлопывание и поправка

Код берёт последний partial как hi, затем до p−1 раз складывает hi с очередным y с конца, вычисляя yr/lo и останавливаясь при ненулевом lo либо исчерпании массива. Масса |hi| плюс модули ещё не обработанных partials подчинена S'≤(1+u)S+h, значит ограничена

**G = (H+ph)/(1−pu)**.

Совокупная ошибка выполненных сложений относительно суммы **обработанных** partials ≤p(uG+h). Необработанный хвост отдельно ограничен в §4; остаток lo последнего сложения уже входит в ошибку сложения, повторно его как хвост не считаем.

Условная финальная поправка имеет вид `y=RN(lo+lo); x=RN(hi+y); yr=RN(x−hi); if yr==y: hi=x`. При отсутствии overflow удвоение binary64 точно, включая subnormal. По P2 для последней тройки |lo|≤3uG+3η. Независимо от знаковых ветвей и результата проверки равенства величина возможного изменения hi не больше

`2|lo|+u(|hi|+2|lo|)+h ≤ (7u+6u²)G+(6.5+6u)η ≤ 8uG+8η`.

Суммируя drift накопления, округления схлопывания, пропущенный хвост и поправку, получаем **равномерную теорему F_OP**:

```
|math.fsum(t) − Σ_exact t_i| ≤ F_p(A),
F_p(A) = L(2uH+2η) + (p+8)uG + 3puH + (4p+8)η,
H=(A+3Lη)/(1−4Lu),  G=(H+pη/2)/(1−pu).
```

Здесь pη/2+3pη ослаблено до 4pη. F_p неотрицательна, монотонна и аффинна по A. Оценка заведомо консервативная O(p²uA) в данной области, не заявленная оптимальная ошибка fsum. Формула конечна и вычислима без L итераций: L — одно целое число.

## 6. Overflow не возникает на охраняемом пути

При |q_i|,|x_i|≤2 каждое exact произведение ≤4, округлённое тоже ≤4 (4 представимо). Значит A≤4p≤2^22. При p≤2^20 имеем 4Lu<2^−12, pu≤2^−33, 3Lη<1, ph<1. Отсюда H<2^23 и G<2^24.

Индукция легитимирует использование §2: перед очередной тройкой T≤H; exact x+y ограничен H, его rounded hi <2H; exact hi−x <3H, затем exact y−yr <5H. Они лежат значительно ниже 2^27, поэтому не overflow, и P1–P3 сохраняют индуктивную массу. Для финальной фазы тот же аргумент с G; удвоение lo и пробная поправка также <2^27. Изначальные входы малы, база выполнена. Никакого предположения «все операции уже конечны, значит доказано» нет. Ресурсные/интерпретаторные ошибки по-прежнему обрабатываются как ошибки, не как числа.

При вычислении самой рациональной F_p на A_prod из §7 значения могут быть чуть больше A, но это точная арифметика неограниченных целых и не выполняет binary64 сложений fsum; её overflow не предполагается. Реальная нехватка памяти ведёт к UNKNOWN/отказу до публикации.

## 7. От fsum к парному box-сертификату

Все величины ниже вычисляются **точно**, над рациональными значениями входных binary64:

```
A_x    = Σ_i max(|l_i|,|h_i|) |x_i|,
P_x    = (1+u) A_x + pη/2,
E_x    = u A_x + pη/2 + F_p(P_x),
U_can  = Σ_i max(l_i(z_i−w_i), h_i(z_i−w_i)) + E_z + E_w.
```

По §2 сумма ошибок произведений ≤uA_x+pη/2 и Σ|t_i|≤P_x. По монотонности F_p и §5 `|s(q,x)−q·x|≤E_x` для каждого q box. Точная support function прямоугольника ограничивает `q·(z−w)` сверху. Поэтому **для каждого q блока**

`s(q,z)−s(q,w) ≤ U_can`.

Решение только **U_can<0**, строгое. U_can=0 или >0 ⇒ UNKNOWN. Версии, S/R/A и стабильность witness остаются условиями внешнего COVER; численная граница их не заменяет. Для каждого изменённого фрагмента обеих сторон требуется успех. Общий max, representative, UTF-8 ties и text_version затем сохраняются по L2–L5.

Не нужен outward float rounding, если решение принимается над точными целыми/Fraction. Перевод U_can в float для сравнения запрещён. Любое будущее интервальное ускорение требует отдельного доказательства округления наружу. Norm tolerance E01 остаётся 1e−12 и не используется в сравнении score.

## 8. Два прежних контрпримера не пропускаются

1. q=w=[0.6,0.8], z=[nextafter(0.6,+∞),nextafter(0.8,−∞)]. Exact real difference `−1801439850948199/81129638414606681695789005144064`, но оба канонических score=1.0. При w.fragment_id=z и z.fragment_id=a winner меняется. U_can≥0, сертификат не выдаётся.
2. q=w=[1,η], z=[1,0]. Exact real difference −η²; произведение η² underflow и оба score=1.0. Новый меньший ID снова важен. Абсолютные η-члены сохранены, U_can≥0.

Контрпримеры сохраняются как отрицательные тесты real-dot подхода; они не исправлены rank epsilon. Новые положительные/граничные случаи, фактические значения U и oracle differences сохранены в `reports/e_stages/E03/E03_2026-11-18_03/numeric_checks.json`.

## 9. Цена и предел результата

Для фиксированного p вычислить α_p,β_p из аффинной зависимости E_x=α_p A_x+β_p один раз. Для одной z,w/box пары нужен один проход p координат для support/A_z/A_w и постоянное число рациональных операций. Никакого q/scorer аргумента у bound нет; query block используется только для заранее оплаченного построения box. Предел `J≤B Σ_d(|R_d|+|A_d|)` даёт O(Jp) точных координатных действий вместо O(Σ|Q_b|t_dp) scoring. Это операция над блоком, не SCAN, замаскированный обозначением.

Bigint цена существенна: exact dyadic products могут иметь знаменатель 2^2148; длина промежуточных целых O(2148+log p) плюс размер рациональных коэффициентов p. Нельзя считать Fraction одной SIMD-инструкцией. Предвычисление α/β, runtime validation, box build, неудачные проверки, exact fallback, postings, память, вывод и embeddings оплачиваются в `complexity.md`. При слабых margins, больших p/широких boxes или малых blocks метод может проигрывать.

**C1-O1 закрыто на уровне спецификации в указанной области и модели исполнения.** Проверки конечных примеров дополняют приведённое доказательство и ручную привязку к машинному коду; они не заменяют их. Это не формальная верификация ISA/CPython/компилятора, не реализация E04 и не доказательство превосходства или научной новизны. При неизвестной сборке/необеспеченных guards действует UNKNOWN; канонический scorer не заменён.
